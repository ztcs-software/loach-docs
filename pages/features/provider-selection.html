Provider selection

Loach is a chat client, not a model. Out of the box it speaks two protocols: Ollama for local models running on your machine, and any OpenAI-compatible endpoint for hosted or self-hosted services. You can keep both wired up at once and switch between them at will.

Local: Ollama

The default backend. Loach talks to an ollama serve process over HTTP and probes it as soon as the app starts, so the models you’ve pulled are in the model picker without a refresh. The picker checks again whenever you change a base URL or key, and has its own refresh button. If Ollama is not running, the picker lists it as Not running and offers to start it for you (see below); the Models tab shows the connection error.

When the chosen model supports them, streaming, multimodal images and thinking-mode reasoning are passed through to the daemon without extra configuration. By default Loach looks for Ollama at http://localhost:11434 - change the Ollama base URL in Settings → Providers if it lives on another machine or port.

Starting Ollama from Loach

You do not have to run ollama serve by hand:

  • Start Ollama - when the daemon is not answering, the model picker in the chat header shows a Start Ollama button. It finds the ollama program (on your PATH or in Ollama’s default install location), starts it on the host and port of your base URL, waits up to 20 seconds for it to answer, then swaps in the model list. Errors - Ollama not installed, a base URL on another machine, a server that exits straight away - show in the menu itself.
  • Auto-launch Ollama - an opt-in switch in Settings → Providers does the same thing every time Loach opens, if nothing is already running. It is off by default (starting a background service is your call) and limited to a base URL that points at this computer - a remote Ollama is not Loach’s to start. The button above has the same limit.
  • Left running - an Ollama that Loach started keeps running after you quit Loach, since other apps may be using it.
  • Keep model loaded - Settings → Features sets how long Ollama keeps a model resident after a reply: 5 min, 30 min, 1 hour or Always. Until you click one, Loach sends nothing and Ollama’s own default applies (OLLAMA_KEEP_ALIVE, or 5 minutes), even though 5 min shows as selected. Once you pick one, it’s sent with every request and overrides the daemon’s default. OpenAI-compatible providers ignore it.

Cloud or self-hosted: OpenAI-compatible

Any endpoint that implements the OpenAI /chat/completions API works. That includes the real OpenAI API, plus vLLM, LM Studio, LiteLLM, OpenRouter, Groq and other proxies. Set the API base URL and OpenAI API key in Settings → Providers; the key is optional for local servers such as llama.cpp, LM Studio and vLLM.

A presets dropdown at the end of the base URL field one-clicks the URL to the documented endpoint for OpenAI, llama.cpp (llama-server), LM Studio, vLLM, or LiteLLM - handy when you switch between local proxies and hosted services.

The catalog is fetched with the saved key - or without one when the base URL points somewhere other than the OpenAI default, since local servers accept keyless requests. With the default URL and no key, Loach skips the catalog request instead of collecting 401s, and clearing the key empties the API model list so the pickers never offer a model that can only fail at send time.

API keys are saved into the OS credential store (Windows Credential Manager, macOS Keychain or the Linux Secret Service), not written into the SQLite database, and never handed to the app’s web view - the Settings field only shows whether a key is stored. The key is sent only over https://, or over http:// to this computer; an http:// server elsewhere on your network gets requests without it.

Test connection

Each provider section exposes a one-click probe so you can verify a base URL (and API key) before opening a chat:

  • Ollama - queries /api/tags and reports Connected with the number of models available, or Connection failed with the error.
  • OpenAI-compatible - calls the endpoint’s /models listing with the stored key and reports the model count or the error. Disabled while there is an unsaved key still in the input (“Save the key first, then test.”).

A failed test adds a hint under the raw error when it recognises the cause: an unreachable server, a URL that doesn’t parse, an unauthorized key, a /models path that wasn’t found, or a blocked link-local address.

The model picker

Every chat has a model dropdown in its header, labelled with the current model and provider. It lists both providers’ catalogs grouped by provider: Ollama, with a green tick when it’s running or an amber warning when it isn’t, and API, which shows the first 30 models the endpoint returns (or Not connected when there is no key). With no Ollama models and no API key, a Configure providers… entry opens Settings → Providers. Picking a model:

  • Persists onto the chat - reloading the app remembers which model that chat last used.
  • Updates the “most recent” pair - used by Default model → Use most recent when starting fresh chats.
  • Unloads the old model - for Ollama, the previous model is released from VRAM and the new one’s parameter cache is warmed for the parameters sidebar.

You can also switch from the composer: /model <name> takes an exact name or a unique part of one, and /list models shows what’s available.

Heads up

You can switch providers mid-conversation. The chat keeps its full message history; only future replies use the new model. Use this freely to compare answers across models without copy-pasting context.

When a request fails

A failed reply ends with a one-line warning that names the provider and base URL, then says what went wrong in plain words - for example “Ollama (http://localhost:11434) - could not reach the endpoint. Is it running and the URL correct?” The common cases:

  • Out of memory - “ran out of memory loading or running the model. Lower the context length or pick a smaller model.” See Performance & VRAM.
  • Key withheld - “API key withheld because the base URL is http:// to another machine. Switch to https:// to authenticate.”
  • Authentication - “API key invalid or expired” (401) or “API key not authorized for this endpoint or model” (403).
  • Reachability - the endpoint could not be reached, the host name didn’t resolve, the request timed out, or the HTTPS certificate is broken.
  • Server answers - endpoint or model not found (404), rate limited (429), an upstream server error (5xx), or a conversation too long for the model’s context window.

Anything else is shown as the provider’s own error text.
